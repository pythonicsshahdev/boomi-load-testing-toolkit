    What the numbers say

    Four things worth taking away

    The network hop is not the cost

    Connect time stayed at or below 0.1 ms in every phase for both requests, because connections are reused. Roughly nine tenths or more of each response is time spent waiting on the server side.

    Network

    Overhead follows warm-up, not load

    At the same 20 requests per second, the Boomi layer added 20 to 22 ms in the second phase and only 3 to 5 ms after the peak. At the 80 requests per second peak it added about 4 ms.

    Boomi layer

    One tail event to chase

    In the second phase, the slowest 1 percent of responses reached roughly 590 to 760 ms through Boomi, and not on the direct path. It could be a pause or early warm-up, and one run cannot say which.

    Needs a repeat run

    No ceiling found yet

    Both paths stayed at zero errors and hit every target rate up to 80 requests per second. This test did not find where the API starts to struggle.

    How to read this

    What this measurement is, and is not

    Derived, not traced

    The Boomi share is the difference between two runs, not a recorded span. It lumps together everything between Boomi receiving a request and answering it.

    One machine

    The load generator, the Atom and the backend shared a single laptop, so these are indicative figures. Absolute numbers on separate hosts will differ, and network time will no longer be near zero.

    Averages on purpose

    For responses this fast, the percentile buckets are too coarse to separate p50 from p95, so the page leans on averages and calls out only the clear tail event.

    To get true per-hop timing

    These steps would turn the derived split into measured spans and find the limit.

    • Add finer response-time buckets so the middle percentiles are meaningful for fast APIs.
    • Correlate each load phase with Boomi execution records and runtime tracing to time the layer's inner steps directly.
    • Repeat the phased run a few times to see whether the second-phase tail event recurs.
    • Push beyond 80 requests per second, across several load generators, to find where errors or latency begin to climb.
